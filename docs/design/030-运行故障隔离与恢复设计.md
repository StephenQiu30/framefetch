# 030 运行故障隔离与恢复设计

- 状态：Accepted for implementation
- 范围：API/Provider 故障隔离、无凭据会话代理探测、下载 Worker 停止预算。
- 来源：2026-09-07 架构调研及用户授权按项目工作流优化。

API readiness 只检查当前核心依赖 PostgreSQL 结构、MinIO、RabbitMQ 和 Valkey，不探测匿名或受控 Runner。Runner 的故障由请求稳定错误和既有 Provider 探针表达；本期不放宽认证、准入、上下文校验或基础设施失败策略。Compose 中 API 不依赖媒体服务启动；下载 Worker 与 Canary 也不等待所有 Provider，仅等待共享工作目录初始化，按正常重试与恢复机制处理启动竞态。

受控 Runner 通过既有加密文件队列发送明确的 probe 操作。代理只响应固定挑战结果，不访问 Chrome、不导出 Cookie、不访问第三方。请求和响应绑定临时公钥及完整请求，限时清理；安装标记不能单独证明可响应。刷新与 probe 是同一严格协议中的两种操作；刷新保留现有三行格式，probe 使用 `probe:<provider>` 明确标识。启用新 Runner 探测前先更新宿主代理，未支持 probe 的代理不能被误判为健康。匿名 Runner 不发送 probe。就绪探测证明代理响应，不证明平台登录或媒体可用。

下载 Worker 使用 60 秒有限排空，容器停止宽限设为 90 秒，Runner 同样保留 90 秒窗口。租约过期后继续使用现有 PostgreSQL 回收和 Outbox 重投，不在本期改变 attempt 预算或状态机。真实断电恢复、跨主机 HA 与平台全量可用性独立验收。

macOS 按需代理显式设置 launchd `ThrottleInterval=1`，避免默认 10 秒启动节流超过 Runner 的 2 秒 probe 预算。代理仍按队列触发、处理完退出；升级此配置后须重新执行代理 install，保留原 runtime-root 与 Chrome profile。
