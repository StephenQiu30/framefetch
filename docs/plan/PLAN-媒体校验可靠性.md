# 媒体校验可靠性排查与方案

本计划落实[产品定位与边界](../design/01-产品定位与边界.md)、[解析引擎](../design/14-解析引擎.md)与[内容导入](../design/08-内容导入.md)的完整文件交付要求。使用 pm-execution 的 strategy-red-team 与 test-scenarios 方法审查方案。

## 1. 决策状态

按用户确认方案实施，目标是同时减少合法视频误拒绝与异常文件误放行。有效技术规则统一维护在 [Design 14](../design/14-解析引擎.md#12-冷启动矩阵)；本计划记录工作包与验收证据。不得用单条视频恢复、平台特例或扩大 FPS 阈值代替通用回归。

## 2. 已验证问题

### 2.1 截图任务

任务 `caf89915-cf28-41e5-8b95-4dddf32e9863` 的元数据解析成功，确认规格为 1080×1920、H.264/AAC、MP4、30fps 档、时长 17 秒。下载第一次执行后终态为 `failed / media_validation_failed`，不是解析阶段失败，也没有自动重试。

同链接在独立普通测试账户的 Web 操作中再次复现。Runner 诊断取得以下最终文件事实：

| 事实 | 结果 |
| --- | --- |
| 平均帧率 | `366750000/12214729`，约 30.025226fps |
| 标称／基准帧率 | `30/1` |
| 视频播放轨道时长 | `146574000 × 1/9000000` = 16.286 秒 |
| 容器时长 | 16.347 秒 |
| 容器声明编码样本数 | 489 |
| 正常 edit list 下实际解码帧数 | 488 |
| 仅作诊断、不应用 edit list 的编码时长 | `146576748 × 1/9000000` = 16.286305333… 秒 |
| 仅作诊断、不应用 edit list 的实际解码帧数 | 489 |
| 完整音视频严格解码 | 退出码 0，错误输出为空 |

故障基线的 `frame_rate.py::probe_frame_rate` 对平均帧率跨档的情况，只在 `avg_frame_rate × duration_ts × time_base == nb_frames` 精确成立、且末帧差异小于一帧时接受标称帧率。该文件的平均帧率对应编码样本时长，`duration_ts` 却对应应用 edit list 后的播放轨道时长；二者混算得到约 488.990832 帧。播放与编码时长相差约 0.305 毫秒，因此精确等式不成立。随后 `verification.py::verify_probe` 把 30.025226 归入 60fps 档，与确认的 30fps 档比较而拒绝，完整解码尚未执行。

控制实验在同一文件上仅改变 ffprobe 的 edit list 读取方式。编码时长下，平均帧率与 489 个样本的等式精确成立。该实验解释了数据口径冲突；不构成关闭 edit list、改写用户文件或直接发布的理由。正常显示帧数与编码样本数本来就不同，不能新增二者强制相等的规则。

### 2.2 故障基线中的诊断与恢复

`verification.py` 的多种拒绝分支都只抛出 `invalid_artifact`，缺少具体字段及比较证据。Runner 的结构化失败最终又被下载执行层投影成 `media_validation_failed` 与字符串 `extractor_broken`；数据库中缺少足以复盘帧率、时长、编码或解码失败的事实。

`DownloadErrorCode.MEDIA_VALIDATION_FAILED.retryable` 为 false；但 Web 终态失败文案称“系统会重新下载并再次验证”。页面同时另有要求用户手动重试的提示，导致行为与承诺冲突。

## 3. 官方资料与技术判断

- [FFmpeg AVStream 定义](https://ffmpeg.org/doxygen/5.1/structAVStream.html)：`avg_frame_rate` 是平均帧率，`r_frame_rate` 是推测的基准帧率，不能直接视为实际显示帧率。`nb_frames` 仅在已知时提供编码层计数。
- [ffprobe 文档](https://www.ffmpeg.org/ffprobe.html)：提供逐帧、逐包与计数能力；区间读取存在 seek 起点偏差，头部或若干区间抽样不能单独证明全片时序与完整性。

据实测与上述定义推断：根因是把不同语义和证据强度的字段压缩成一个 FPS 数值，再使用过强的等式证明一致性。修复对象应是媒体事实的口径与验证流程，不能只处理 X 或 30fps。

## 4. 推荐方案

### 4.1 统一媒体事实与时间口径

在已有 Runner 探测、规格选择与最终校验链上定义同一份有类型的内部媒体事实；不增加另一条下载实现。

- 区分上游声明、有限头部探测、编码样本事实、正常播放时间线事实与完整解码事实，标明事实来源、覆盖范围和缺失原因。
- 保留原始有理数、time base 与整数时间戳。播放时长、编码样本时长、容器时长、起始偏移分别保存，运算只比较同一口径。
- 编码包数、声明样本数与显示帧数分别保存。edit list、B 帧重排、编码器延迟与末帧时长均不能被压缩成“帧数不一致”。
- 候选探测与最终校验共用帧率解释和档位函数；有限探测只声明其实际覆盖，不把局部 CFR 推断推广为全片证明。

### 4.2 按证据冲突升级验证

保留廉价元数据检查与既有完整音视频解码。只有帧率证据跨档、缺失或矛盾时，追加本地全文件的帧／包时间线核验：

1. 首先排除容器、编码、尺寸、音轨、作品身份与完整时长的确定不匹配。
2. 相同时间口径的事实足以确认规格时，继续完整解码；存在矛盾时进入时间线核验，不直接借用 `r_frame_rate`。
3. 对正常播放时间线的全部可显示帧进行流式统计，使用有理数分析实际 cadence、整体速率、变帧率和时间戳异常。编码样本事实只用于解释 edit list 与封装差异。
4. 真实 VFR 的规格含义必须先明确：保留实际 VFR，不静默降帧、复制补帧或转码；不能仅凭平均值低于阈值掩盖高帧率区段。无法证明与已确认规格一致时要求重新解析并展示准确规格。
5. 帧扫描沿用原下载截止时间、取消与子进程组回收。使用有界内存的流式统计与固定大小摘要；现有 Supervisor 默认输出截断不能直接承载整片 JSON 帧清单。预算耗尽或摘要截断必须记为证据不足／校验超时，不能误称文件损坏。

不得关闭 edit list 作为正常验证或播放行为，不更改全局 `30.01/60.01` 阈值，不按平台、URL、分辨率或当前误差值增加放行条件。

### 4.3 失败证据与恢复闭环

- 保留现有十三类执行分类与业务 `media_validation_failed` 投影；增加可序列化、无秘密的校验子因，例如实际规格不匹配、时间口径冲突、音视频轨截断、解码失败、证据不充分。
- 子因包含校验规则、阶段、期望与实测有理数、证据来源、覆盖范围和终止原因；使用白名单，不保存原始 stderr、媒体 URL、Cookie 或完整 Provider 响应。
- Runner → Worker → 持久化 → API → 页面应保留同一份非敏感证据。公开字段变化时按服务端 → Web → Electron／App 契约顺序同步。
- 自动重试只对应可恢复传输／运行时故障；确定规格冲突不重复下载。终态失败显示具体原因与手动恢复动作；只有真实 `retry_wait` 才承诺自动重试。
- 引擎修订覆盖新规则；旧 inspection 要求重新解析与确认，不用新规则悄悄执行旧规格。

## 5. 方案关键假设审查

评分为方案影响、反例可能性、验证成本低的程度，各 1–3，乘积仅用于工作排序。

| 排序／分数 | 关键假设与最强依据 | 失效条件 | 最便宜的验证与停止条件 |
| --- | --- | --- | --- |
| 1／27 | 分开编码与播放口径能解释截图误差；同一文件控制实验已有支持 | 新规则仍要求编码数等于显示数，或需忽略 edit list 才通过 | 对本文件、带 edit list 的合法剪辑、无 edit list 文件对照；任一合法编辑被当作丢帧，即否决规则 |
| 2／18 | 全文件时间线比标称帧率可信 | 仅看中位数或头部，漏掉后半段 VFR／真实高 FPS | 合成前 30fps 后 60fps、重复／倒退 PTS 与 B 帧样本；高 FPS 被误放行为 30fps 即停止 |
| 3／18 | 正常元数据快路径不会放过损坏文件 | 仍可只靠头部／容器时长发布，长音轨掩盖短视频 | 截断尾部、少分片、短视频长音轨、损坏帧负例；任一发布成功即停止 |
| 4／12 | 额外核验可在已有资源预算内完成 | 长片扫描被 64KiB 输出截断、内存增长或取消不能终止子进程 | 长片与大量帧样本，注入超时／取消；突破已有截止时间或内存无界即改实现，不能放大资源上限掩盖 |
| 5／12 | 结构化子因能使用户做出正确恢复动作 | Worker 丢失证据、终态仍承诺自动重试、重试静默换规格 | 从真实 Runner 失败走到数据库和 Web；任一层只剩通用字符串即未完成 |

保留完整解码、原始时长核验、上下文绑定与内容保护边界有充分依据。VFR 与时间线的实现规则见 Design 14。长片端到端耗时仍须独立验收；定长统计和合成流式测试不能证明多小时真实文件在预算内完成。

## 8. 验证证据与限制

本轮当前运行环境的详细证据保存在忽略入库的 `artifacts/quality/20261020/`：浏览器截图、视频、编码／播放时间线对照和全平台矩阵报告。测试账户独立于现有用户；全平台基线采用已有服务与身份，未执行冷启动 `--all`，不据此声明冷启动验收通过。

故障基线的 Runner 校验与命令测试 163 项通过，但没有覆盖本文件的 edit list 口径冲突，不能证明该类问题已解决。修复后的回归和正式产品结果单独记录。

### 8.1 平台基线终态

全部 25 个已接入平台的 55 条样本已执行：50 条正例中 46 条取得正式完整文件并通过长度、SHA-256、ffprobe 与独立全音视频解码；22 个平台两条正例均通过。Reddit 为 1/2，第一条重跑由 `extractor_broken` 变为 `login_required`；小红书为 1/2，第一条重复 `content_unavailable`；红果为 0/2，两条均在 L3 返回 `browser_parser_missing`。另有 5 条受保护负例，仅 2 条取得符合原有标准的拒绝证据；其余分别受 YouTube 限流、优酷挑战和腾讯样本证明缺口影响。

准备阶段的测试账户额度限制与脚本重复登录限流已通过隔离测试配置和会话复用解决，受影响平台已重跑，未将准备失败计入上述平台结果。测试结束后恢复测试账户专属额度为默认值，既有用户和全局配额未修改。

Reddit 身份限制、小红书失效样本、红果回退解析器缺失应分别跟踪。媒体事实校验方案不能替代 Provider 能力补齐，也不能证明未来平台风控已解除。

### 8.2 Web 与分析基线终态

使用指定 agent-browser 对 11 个页面完成桌面／390px、明／暗四种组合，共 44 次检查。未观察到横向溢出或页面运行错误。22 次 axe 审计中，一次在视频分析加载占位状态报告 skeleton 上的无效 ARIA，尚未稳定重复；另有键盘提示 ARIA 与对比度 incomplete 项，因此不宣称可访问性全部通过。

真实动作覆盖登录、全平台列表翻页、截图链接解析与失败复现、下载记录搜索、本地视频上传与播放、合成剧本上传与规范化展示、视频逐镜拉片、剧本审阅和人物页切换。两项分析均成功；MD／DOCX 及视频原生 ZIP 共 5 个产物经正式导出 API 取回并通过文本／ZIP 容器完整性检查。未将 API 取回等同于浏览器系统保存落盘，也未进行全部分析模式或专业内容质量验收。

该基线未覆盖真实邮箱收信与完成注册、浏览器系统保存最终落盘、去水印完整处理、删除确认后的实际清理、管理员专属页面、原生 Electron／App、全量冷启动和真实身份失效恢复。详细矩阵、截图和限制见证据目录中的 `report.md` 与 `platform-matrix.json`。


## 9. 修复验收结果

统一规则与失败证据已落地，技术定义见 Design 14。媒体事实解释及时间线统计位于 `backend/app/services/downloads/rules/`，Runner 与正式 HTTP 验收共享纯规则；验收仍独立取回和探测发布文件。没有 URL／平台／分辨率放行特例，不改变 FPS 阈值、正常 edit list 或全音视频严格解码。

### 9.1 自动化和资源验证

- 后端 3832 项通过、5 项跳过；Ruff 检查／格式、mypy 通过。跳过一个隔离 MinIO 未配置的上传边界项和四个 Windows 原生权限项。
- Web 660 项测试、格式、lint／类型、生产构建与 OpenAPI 生成无差异检查通过；HTTP 契约未增加字段，App 冻结快照无变化。
- Electron 已同步上游文案，来源检查、lint／类型、42 项单元测试、构建及 10 项夹具端到端通过；不等同于真实原生服务流程。
- 正反例覆盖常见与 NTSC 帧率、编辑端点、VFR 前低后高、毫秒时间基下轻微超档长区段、全区段穷举对照、缺失／重复／倒退时间戳、真实损坏编码包、规格／时长不符、输出流、取消／超时和进程组回收、白名单与事务事件。新增反例均先观察到失败，再验证修复。
- 20 万帧统计实验约代表 111 分钟的 30fps 时间戳，耗时 4.63 秒，tracemalloc 峰值 189165 字节；这只验证统计路径，不能替代多小时真实媒体全解码预算验收。
